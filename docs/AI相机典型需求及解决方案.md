# AI相机典型需求及解决方案

## 1. 文档目的

本文基于当前 `turnkey` 工程的页面实现，按“页面入口 -> 业务动作 -> 底层能力”的顺序，梳理一套 AI 相机产品常见的通用功能，以及本项目当前采用的实现方案。

这份文档重点回答三个问题：

- 页面层实际覆盖了哪些典型相机需求
- 这些需求在代码里是如何被拆到 `page_manager`、`media_manager`、`param_manager`、`file_manager`、`power_manager` 等模块中的
- 哪些能力已经闭环，哪些能力目前还是入口已在、链路未完成

## 2. 页面功能树

当前页面注册关系如下：

```text
home
|- photo
|  |- photo_settings
|  \- video
|     \- video_settings
|- ai_photo
|  |- ai_photo_settings
|  |- ai_style_preview
|  \- ai_recognition_preview
|- album
|  |- photo_preview
|  \- video_album
|     \- video_preview
|- system_settings
|  |- wifi_list
|  \- version_info
|- chat
\- test
```

从产品结构看，这套 UI 已经具备一个相机产品最常见的几条主链路：

- 首页入口链路：拍照、AI拍照、相册、设置
- 拍摄链路：拍照模式、录像模式、参数设置
- AI链路：AI模式选择、风格化预览、识别预览
- 资产链路：照片相册、视频相册、照片预览、视频回放
- 系统链路：WiFi、音量、自动息屏、格式化、恢复出厂、版本信息

## 3. 总体实现思路

从页面逻辑反推，这个项目采用的是比较典型的“页面层薄、业务层集中、系统状态统一广播”的结构。

### 3.1 页面层

- `page_manager` 统一管理 `create/show/hide/update/back`
- 每个页面只维护自己的容器、局部控件和局部事件
- 页面跳转不直接等于业务动作，必要时先调用业务层再跳转

### 3.2 业务编排层

- `media_manager` 负责拍照、录像、模式切换、参数下发、格式化等动作
- `message_manager` 负责和 `MODEMNG/EVENTHUB` 交互，处理同步等待与结果 topic
- `file_manager` 负责媒体列表、缩略图、容量估算、删除、格式化封装
- `player_manager` 负责视频播放控制
- `wifi_manager` 负责扫描、连接、开关、连接结果查询
- `image_process_manager` / `image_recognition_manager` 负责 AI 异步处理

### 3.3 状态管理层

- `param_manager` 是页面可读写的统一状态源
- 典型状态包括分辨率、ISO、曝光、音量、WiFi、SD卡、电池、AI模式、变焦、对焦框状态
- 页面通过 `param_manager_register_callback()` 做 UI 回显，不直接互相读页面内部状态

### 3.4 顶层通用 UI

- `status_bar` 负责 SD/WiFi/电池等跨页面状态展示
- `top_notice` 负责全局提示、阻塞提示、短时反馈
- `volume_bar` 负责全局音量提示
- `gesture_back` 负责统一的边缘滑动返回
- `zoom_bar`、`filter_panel` 是直播画面类页面共享的控制组件

## 4. 典型需求及解决方案

### 4.1 首页能力聚合

### 需求

AI 相机通常需要一个轻量首页，把“拍照、AI拍照、相册、设置”等高频入口集中起来，同时尽量不让首页承担复杂业务。

### 当前方案

- `page_home.c` 只做入口聚合，不持有复杂业务状态
- 点击“拍照”时，先通过 `media_manager_execute(MEDIA_OP_SWITCH_TO_PHOTO_MODE, 0)` 切到拍照模式，再进入 `photo`
- 点击“AI拍照”时，先切拍照模式，再将分辨率强制设为 `12M`，然后进入 `ai_photo`
- 点击“相册”前先检查 `PARAM_ID_SD_READY`，未插卡则直接提示
- 首页只维护一个时间定时器，不做重业务轮询

### 设计价值

- 首页保持薄，适合作为产品导航壳
- 入口处就完成必要的模式预热，减少目标页的前置判断

### 4.2 普通拍照模式

### 需求

普通拍照页通常需要同时解决以下问题：

- 展示当前分辨率和剩余可拍张数
- 响应物理拍照键和对焦键
- 对焦状态有可视反馈
- 支持滤镜、变焦、设置入口
- 返回时恢复首页工作模式

### 当前方案

- `page_photo.c` 负责直播页 UI，顶部显示返回、分辨率、剩余张数，底部显示模式切换、滤镜、菜单
- 剩余张数通过 `file_manager_get_remaining_photo_count()` 估算，而不是等拍满才报错
- 拍照动作统一走 `media_manager_execute(MEDIA_OP_TAKE_PHOTO, 0)`，成功后通过 `top_notice` 提示最新文件名
- 对焦键分成三段语义：
  - 按下：单次对焦
  - 长按 3 秒：关闭 AF，进入锁焦框状态
  - 释放：恢复 AF，隐藏对焦框
- 对焦框不由页面内部定时器驱动，而是由 `PARAM_ID_FOCUS_FRAME_STATE` 驱动，页面只负责订阅和渲染
- 返回时除了 `page_manager_back()`，还会先切回 `boot` 模式，并重置变焦、关闭滤镜面板

### 设计价值

- 物理键行为与触屏 UI 在同一页面统一编排
- 对焦框状态被抽成参数，普通拍照页和 AI 拍照页都能复用

### 4.3 录像模式

### 需求

录像模式除了模式切换外，通常还需要：

- 一键开始/停止录像
- 录制中显示录制时长和闪烁红点
- 显示剩余可录时长
- 录制期间防误触
- 关机前安全停录

### 当前方案

- `page_video.c` 用 `KEY_ID_CAMERA` 做录像开始/停止切换
- 通过 `record_ui_timer` 更新红点闪烁和录制时长
- 通过 `remaining_time_timer` 周期刷新剩余录制时长
- 剩余时长来自 `file_manager_get_remaining_video_seconds()`，按分辨率估算空间
- 录像开始后，页面会屏蔽 TP 和非相机类按键，降低误操作概率
- `power_manager_register_shutdown_prepare_cb()` 被注册到录像页，长按关机前会先尝试停录
- 退出录像页时恢复输入屏蔽状态，并重新允许自动息屏

### 设计价值

- 录像页把“录制态”和“非录制态”当成两个不同交互模式处理，而不是简单换图标
- 通过 `shutdown_prepare_cb` 把相机关机安全性纳入页面逻辑

### 4.4 拍照/录像参数设置

### 需求

相机设置页的核心诉求不是“把选项显示出来”，而是：

- 设置项和底层能力一一对应
- 修改后立即回显
- 失败时不要把 UI 和底层状态弄乱

### 当前方案

- `page_photo_settings.c` 支持：
  - 分辨率
  - 白平衡
  - ISO
  - 曝光
  - 画质
  - 人脸检测
  - 笑脸抓拍
- `page_video_settings.c` 支持：
  - 视频分辨率
  - 白平衡
  - 曝光
  - ISO
- 滚轮型设置通过 `media_manager_execute()` 下发到业务层
- 开关型设置优先走 `media_manager`，仅在没有底层动作时才直接写 `param_manager`
- 页面 `update()` 会从 `param_manager` 重新拉取当前值，避免页面返回后显示陈旧状态

### 设计价值

- 页面不直接拼消息到 `MODEMNG`
- 设置页本质上只是参数编辑器，底层动作统一留给 `media_manager`

### 4.5 直播画面的通用控件复用

### 需求

拍照和录像页面通常共享一批直播控制能力：

- 变焦
- 滤镜
- 对焦框
- 状态栏
- 边缘返回

### 当前方案

- `zoom_bar.c` 是全局单例，支持 `1x / 2x / 3x / 6x`
- `filter_panel.c` 是全局单例，负责滤镜条、聚焦框、滚动吸附、滤镜参数同步
- `status_bar.c` 在 `lv_layer_top()` 上展示，不跟随页面销毁
- `gesture_back.c` 统一处理左边缘右滑返回，页面只负责注册和激活当前回调

### 设计价值

- 拍照/录像页只关心“何时显示/隐藏”，而不重复造控件
- 顶层组件放到 `top layer`，跨页面切换时视觉更稳定

### 4.6 AI拍照模式

### 需求

AI 相机一般不会重新做一套拍摄底层，而是在“普通拍照能力”之上再叠加 AI 模式选择和拍后处理。

### 当前方案

- `page_ai_photo.c` 延续普通拍照页的主结构：剩余张数、对焦框、拍照键、对焦键、AI键
- `page_ai_photo_settings.c` 提供三个 AI 模式：
  - 风格变换
  - AI识万物
  - 拍照翻译
- AI 模式值统一存到 `PARAM_ID_AI_MODE`
- AI 拍照完成后，根据 `PARAM_ID_AI_MODE` 决定下一页：
  - 风格变换 -> `ai_style_preview`
  - AI识万物 -> `ai_recognition_preview`

### 设计价值

- AI 模式被设计成“普通拍照的一个扩展分支”，而不是完全独立的拍摄系统
- 这样可以最大限度复用普通拍照的 SD 校验、剩余张数估算、按键语义和对焦逻辑

### 4.7 AI结果页与异步任务

### 需求

AI功能最大的不同在于它是长耗时任务，UI 需要处理：

- 拍后自动进入结果页
- 后台处理不中断 UI
- 用户可看到处理中、成功、失败三种状态
- 结果页能重新触发一次 AI 动作

### 当前方案

#### 风格化预览

- `page_ai_style_preview.c` 进入时刷新最新照片，默认显示原图
- 底部样式面板支持左右滚动和吸附，当前选项由 `selected_style_index` 管理
- 按 AI 键后才真正启动 `image_process_manager_start_style()`
- 页面通过定时器轮询 `image_process_manager_get_state()`
- 成功后把结果路径替换为新图；失败则弹出全局提示
- 从页面行为看，风格化前必须 `WiFi 已开启且已连接`
  - 这是代码行为结论，说明风格化链路当前被当作联网能力处理

#### 万物识别预览

- `page_ai_recognition_preview.c` 进入时自动刷新最新照片并立即开始识别
- 识别过程使用 `image_recognition_manager` 后台线程 + 页面轮询的模式
- 识别完成后直接把文本写入右侧文本框
- 用户可以按 AI 键再次触发识别

### 设计价值

- 把 AI 任务抽到 manager 层以后，页面只需要处理“状态轮询 + 结果回显”
- 这套模式非常适合后续扩展到 OCR、翻译、摘要、云端增强等更多 AI 能力

### 4.8 相册、预览与删除

### 需求

相机产品必须有完整的拍后资产闭环：

- 照片/视频浏览
- 大量媒体时仍保持流畅
- 进入预览后返回原位置
- 支持批量选择和删除

### 当前方案

#### 照片相册

- `page_album.c` 使用虚拟列表/复用池，而不是把所有缩略图一次性创建出来
- 支持九宫格滚动、快速滚动条、滚动进度提示
- 长按进入选择模式，支持多选、全选、批量删除
- 删除期间会屏蔽输入并显示阻塞提示
- 从照片预览返回时，会记住上一次照片索引并自动滚回对应位置

#### 照片预览

- `page_photo_preview.c` 使用“双图层 + 跟手位移”的左右滑动方案
- 普通左右滑动用于上一张/下一张切换
- 左边缘右滑复用 `gesture_back` 实现返回，不和翻页手势抢行为

#### 视频相册与视频预览

- `page_video_album.c` 基本复用了照片相册的虚拟列表、选择、删除、快速滚动逻辑
- 进入 `video_preview` 前，会先判断当前是否已处于回放模式
- 如果还不是回放模式，先切换到 `playback mode`
- `page_video_preview.c` 使用 `player_manager` 实现：
  - prepare
  - play/pause
  - seek
  - 上一条/下一条切换
  - 进度条轮询
- 退出视频预览时，会恢复进入前的 work mode，避免用户回不去拍照/录像现场

### 设计价值

- 相册和预览并不是“查看图片”这么简单，而是和工作模式、删除安全、滚动性能绑定在一起
- 当前实现已经具备一个完整相机媒体闭环应有的基本形态

### 4.9 系统设置、WiFi与设备状态

### 需求

相机类产品除了拍摄能力，还必须处理一批设备级需求：

- WiFi 开关、扫描、连接、密码输入
- 音量调节
- 自动息屏
- 格式化存储
- 恢复出厂
- 版本信息
- 页面顶部状态图标同步

### 当前方案

- `page_system_settings.c` 是系统级设置入口
- 已闭环的设置有：
  - WiFi设置
  - 音量设置
  - 自动息屏
  - 格式化
  - 出厂设置
  - 版本信息
- 格式化和恢复出厂不是直接在点击回调里执行，而是通过一次性 `lv_timer` 延后执行
  - 这样可以避开事件回调里直接做长耗时操作
- `page_wifi_list.c` 支持：
  - WiFi 开关
  - 扫描
  - 密码输入弹层
  - 异步连接轮询
  - 已保存/已连接状态展示
- `status_bar.c` 订阅 `param_manager`，在顶层统一展示 SD/WiFi/电池状态
- 不同页面会按上下文决定状态栏显示哪些图标

### 设计价值

- 把设备管理能力放入独立页面，避免拍摄页被系统配置打断
- 状态栏与设置页都以 `param_manager` 为单一状态源，降低状态不一致风险

### 4.10 物理按键、电源与手势返回

### 需求

相机不是纯触屏设备，必须把物理按键、电源策略和手势一起考虑：

- 拍照键、对焦键、AI键、音量键、电源键要能共存
- 自动息屏不能影响拍摄/录像
- 熄屏后任意输入要可唤醒
- 长按关机前要给关键页面收尾机会

### 当前方案

- `key_manager` 统一抽象物理按键事件，支持点击、长按、3 秒长按、连发
- 音量键默认直接调节系统音量
- 拍照页/录像页/AI页各自按需注册和注销自己的物理键回调
- `power_manager` 提供：
  - 自动息屏
  - 输入唤醒
  - 电源键短按亮灭屏
  - 电源键长按两阶段关机
- 拍照页和录像页显示时会禁用自动息屏，退出后恢复
- `gesture_back` 让“边缘返回”成为统一交互，不需要每个页面重新做手势状态机

### 设计价值

- UI 行为不只受触摸驱动，而是和硬件输入、屏幕状态一起被系统化管理
- 这是相机类 UI 和普通 App UI 的关键区别之一

## 5. 当前实现边界

从页面逻辑看，当前工程已经覆盖了相机产品的大部分通用能力，但也存在几处明显的“入口已在、链路未闭环”：

- `拍照翻译` 仅出现在 AI 模式枚举和设置页中，拍照完成后没有进入翻译页，也没有对应的翻译 manager
- `AI识万物` 页的“朗读文本”按钮当前只有日志，没有接 TTS
- `chat` 页面目前只是 UI 壳，按住说话和音色按钮都还没有业务实现
- `系统设置` 里的语言、时间和日期目前是展示项，还不是可编辑闭环

这些点说明当前项目已经从“相机基础能力”走到了“AI相机产品雏形”，但在更完整的 AI 体验上还处于持续补齐阶段。

## 6. 对后续需求拆分的建议

如果后续继续扩展 AI 相机能力，建议优先沿着当前代码已经形成的模式继续演进：

- 新的拍摄类能力优先复用 `photo/video` 页的模式，不要绕开 `media_manager`
- 新的 AI 能力优先复用“结果页 + 异步 manager + 轮询状态 + top_notice”的模式
- 新的设备级能力继续收口到 `param_manager` 和 `system_settings`
- 新的跨页面浮层优先放到 `lv_layer_top()`，避免和页面生命周期耦合
- 新的媒体浏览能力继续复用“虚拟列表 + 快速滚动条 + 返回定位”的相册模式

## 7. 总结

从页面逻辑出发，这套 AI 相机实现已经不是单点功能 Demo，而是一套较完整的相机 UI 壳：

- 有拍照、录像、AI拍后处理、相册、预览、回放、设置、WiFi、电源管理等完整主链路
- 页面层主要负责交互和展示，业务动作被收敛到 `media_manager/file_manager/wifi_manager/...`
- `param_manager + top layer + 异步 manager` 这三类机制，已经形成了比较稳定的通用解决方案

对后续迭代来说，最值得继续沿用的是这套“页面负责组织体验，manager 负责落地能力”的拆分方式。
